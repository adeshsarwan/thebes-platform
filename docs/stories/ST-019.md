# ST-019 - Website Registry & Configuration Console

## Story Scope

ST-019 implements the first operator-facing Website Registry in `adeshsarwan/thebes-platform`.

The console lets an authenticated Thebes operator manage publisher websites, logical ad units, serving mode, and experiment traffic split for the existing ST-004 pilot SDK configuration.

Out of scope for this story:

- pricing engine, pricing API, pricing storage, and pricing validation
- retry engine, retry API, retry storage, and retry validation
- analytics, reporting, ROI, campaigns, media buying, Creative Central, or SDK redesign
- production Worker, production D1, DNS, `cdn.thebesads.com`, and Price Optimizer production changes

## Existing ST-004 Pilot D1 Tables

The ST-004 pilot D1 database `thebes_sdk_pilot` remains the authoritative persistence source. ST-019 does not create duplicate website, placement, or configuration tables inside the platform service.

Existing tables reused by ST-019:

- `publishers`
  - Website identity and operational enablement.
  - Key columns: `site_id`, `site_key`, `domain`, `display_name`, `enabled`, `gam_network_code`, `telemetry_json`, `downstream_modes_json`, `created_at`, `updated_at`.
- `placements`
  - Logical ad unit configuration for one website.
  - Key columns: `placement_id`, `site_id`, `placement_key`, `format`, `gam_ad_unit_path`, `mobile_sizes_json`, `desktop_sizes_json`, `min_viewport_width`, `request_mode`, `trigger_json`, `pricing_json`, `enabled`, `created_at`, `updated_at`.
  - `dom_id` exists as legacy schema compatibility only. ST-019 does not collect or write DOM IDs.
- `publisher_config_versions`
  - Versioned active runtime configuration consumed by the SDK Worker.
  - Key columns: `config_version_id`, `site_id`, `version`, `manifest_hash`, `config_json`, `active`, `created_at`.

Relationships:

- One `publishers` row owns many `placements` rows.
- One `publishers` row owns many `publisher_config_versions` rows.
- Runtime reads use the active config version where `publisher_config_versions.active = 1`.
- ST-019 writes update current website/ad-unit rows and then create a new active `publisher_config_versions` row. Previous versions remain inactive for history.

## Current Active-Version Mechanism

The ST-004 Worker resolves active runtime configuration by:

1. Normalizing the request hostname.
2. Looking up an enabled publisher by `publishers.domain`.
3. Joining to `publisher_config_versions`.
4. Returning the latest active row where `active = 1`.

The active runtime config is the `config_json` payload. ST-019 must never mutate that JSON in place.

Every approved save follows this sequence:

1. Validate the complete website, placement, or serving change.
2. Read the authoritative publisher and placement rows.
3. Generate the complete ST-004-compatible runtime config.
4. Validate required runtime fields and confirm default placement targeting remains empty.
5. Insert the new `publisher_config_versions` row with `active = 0`.
6. Activate the new row and deactivate previous rows for the same `site_id`.
7. Confirm exactly one active version remains and that it is the new version.
8. Return success only after confirmation.

The insert, activation update, and confirmation read use the D1 batch API through the server-side adapter, so prior active rows are not deactivated before the new version has been inserted successfully. Prior version rows are preserved for history.

## Runtime Configuration Generation Path

ST-019 generates runtime config from the authoritative D1 rows:

1. Read the website from `publishers`.
2. Read enabled and disabled logical ad units from `placements`.
3. Preserve existing `placement_id`, `pricing_json`, `trigger_json`, `request_mode`, sizes, format, and enabled state.
4. Build the ST-004-compatible runtime config object:
   - `site_id`
   - `site_key`
   - `domain`
   - `display_name`
   - `enabled`
   - `gam_network_code`
   - `config_version_id`
   - incremented `config_version`
   - `sdk_version`
   - telemetry and downstream modes
   - placements
   - `generated_at`
5. Add ST-019 serving configuration metadata in a forward-compatible top-level `serving` object. The public publisher SDK ignores unknown fields.
6. Insert a new inactive row into `publisher_config_versions`.
7. Activate the new row, deactivate previous rows for that website, and confirm exactly one active version in the same D1 batch.

Default publisher GAM requests remain clean. The config generator does not add Thebes custom targeting keys.

## Server-Side Integration Approach

The browser never connects to D1 and never receives Cloudflare credentials.

The platform service owns:

- operator UI pages
- authenticated operator JSON routes
- domain normalization
- request validation
- operator authentication
- production-safety checks
- repository/service abstractions
- audit-friendly operator responses

The existing pilot D1 owns:

- websites/publishers
- logical ad units/placements
- configuration versions
- active runtime configuration

Integration flow:

```text
Operator browser
  -> authenticated thebes-platform UI/API
  -> WebsiteRegistryService
  -> PilotD1WebsiteRepository
  -> Cloudflare D1 REST API query endpoint
  -> existing thebes_sdk_pilot D1
  -> active config consumed by the ST-004 SDK Worker
```

The server-side Cloudflare adapter uses the official D1 query endpoint:

`POST /accounts/{account_id}/d1/database/{database_id}/query`

Required server-side environment values:

- `OPERATOR_SECRET`
- `CLOUDFLARE_ACCOUNT_ID`
- `CLOUDFLARE_API_TOKEN`
- `THEBES_PILOT_D1_DATABASE_ID`

No Cloudflare or operator secret is embedded in browser JavaScript.

## Validation Rules

Domain normalization:

- lowercase
- remove protocol
- remove path and query
- remove trailing slash
- remove leading `www.`
- reject invalid hostnames

Website rules:

- environment must be `pilot` for writes
- production writes are blocked
- `site_key` is derived internally from normalized domain
- `display_name` is derived internally from normalized domain
- GAM network code must be numeric
- duplicate domains are rejected
- existing `display_name` values are preserved when a website is saved without changing its domain

Ad unit rules:

- placement key must be unique per website
- placement key must be a lowercase logical key such as `anchor`, `native`, `rewarded`, or `interstitial`
- GAM path must begin with `/<network-code>/`
- DOM IDs, selectors, coordinates, layout metadata, and runtime elements are not stored

Configuration rules:

- serving mode is one of `default`, `waterfall`, or `experiment`
- traffic split percentages are integers from 0 to 100
- control and experiment totals must equal 100
- quick presets are `90 / 10`, `80 / 20`, `70 / 30`, `60 / 40`, and `50 / 50`
- presets are UI helpers only; the persisted contract stores explicit integer values
- pricing and retry appear as disabled placeholders only
